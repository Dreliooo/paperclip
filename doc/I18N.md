# UI translations (i18n)

The board UI uses i18next (`ui/src/i18n`). Catalogs live in
`ui/src/i18n/locales/<locale>.json`.

## Rules

- **Complete locales** (`COMPLETE_LOCALES` in `ui/src/i18n/locales.ts`, today
  `en` and `es`) must translate every English key; they are the only languages
  offered in Profile → Display preferences. Other catalogs are partial and fall
  back to English per key.
- Every new user-visible string goes through `t()`:
  `const { t } = useTranslation()` from `@/i18n`, called at the top of the
  component. Never call `t()` at module level.
- Add the key to `en.json` **and** `es.json` in the same change. Plurals use
  `key_one` / `key_other` with `{ count }`. Placeholders (`{{name}}`) must match
  English exactly; no HTML or new URLs inside translations
  (`ui/src/i18n/locale-validation.ts` enforces this in tests).
- Never translate data: names of agents, projects, tasks, people and
  companies, model ids, identifiers, paths, code or logs.
- Spanish copy uses voseo ("Seleccioná", "Probá de nuevo").

## Language selection

Each person picks a language in Profile → Display preferences. The choice is
stored server-side (`user_preferences.locale`, `GET/PATCH
/api/user-preferences/me`) and applied on every sign-in; the browser keeps a
cached copy (`paperclip:locale`) to avoid an English flash on reload.

## Coverage

Translated: navigation sidebar, Decisions (feed, origin context), Dashboard,
Projects, Profile, Agents org explorer, usage/costs breakdown, cache indicator,
read-aloud controls, live run status. Remaining pages still render English
until converted; convert a page by moving its literals to keys as above.
